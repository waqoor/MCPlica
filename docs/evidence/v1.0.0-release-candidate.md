## Candidate scope

The candidate establishes root SemVer authority, synchronized package/API/runtime/image metadata,
versioned release notes and changelog, support/compatibility/API/Compose/troubleshooting guidance,
repository templates/labels/ownership policy, deterministic documentation checks, and a tag-only
release workflow. The workflow refuses reused identities and requires successful CI and Security
push runs on the exact tagged `master` commit before it builds, scans, pushes, signs, attests, and
publishes source/image artifacts.

Tracked browser scratch output and superseded agent handoff/evidence notes were removed. Root-level
`.runtime-*` directories are now excluded from both Git and Docker build contexts and rejected by
repository validation if force-added. The empty funding configuration was removed; sponsorship
documentation says to add a platform configuration only after a verified funding channel exists.

## Disposable Compose and MCP acceptance

All application images were built from the frozen locks through `infra/compose.yaml`. Metadata
validation confirmed `1.0.0`, repository source, AGPL-3.0-only, non-empty revision labels, expected
non-root users, and the embedded runtime version for `mcplica/backend:test`,
`mcplica/runtime:test`, and `mcplica/frontend:test`.

The final acceptance used a new `mcplica-v1rc` project, unique networks, a private generated
environment, an empty runtime root, and new named volumes. During the preparation, side-by-side
testing exposed two harness isolation defects: the project name was not persisted and backend
services still selected the default service-level env file. `prepare_compose.py`, `init_env.py`,
Compose, tests, and operator documentation now bind `COMPOSE_PROJECT_NAME` and
`CONTROL_PLANE_ENV_FILE` to the selected disposable installation. All evidence below comes from a
fresh teardown/recreate after those fixes; the earlier mixed-project run is not counted.

Final service evidence:

- all 13 Compose services reached their required states before and after acceptance;
- 11 long-running services were healthy and both `migrate` and `runtime-init` exited 0;
- two builds reached READY with 100 percent expected-operation coverage;
- three deployments covered initial activation, source-change replacement, and immutable-build
  rollback;
- the initial and rollback runtimes exposed four tools; the updated runtime exposed five;
- authenticated MCP calls preserved GET, POST, PATCH, DELETE, paths, payloads, statuses, and
  upstream bearer authentication;
- one documentation resource was read, one operation was added by the build diff, and the export
  contained five expected files;
- the published runtime continued serving while the AI fixture, API, builder worker, and Milvus
  were unavailable;
- active build/deployment state and authenticated MCP execution survived forced recreation of the
  database, cache, API, workers, and frontend without deleting volumes;
- real Milvus project/generation/attempt isolation, repeat upsert, and scoped cleanup passed;
- the real Chromium UI authenticated, navigated the generated project, verified five operations
  and indexed-document evidence, opened the deployment, observed Running/Healthy, and reported no
  CSP violations.

The final workflow reported 93.143 seconds total, 5.353 seconds for the first build, 9.279 seconds
for the first deployment, and 0.398 seconds for the four-call MCP round trip. The JSON and bounded
redacted Compose/browser diagnostics stayed under ignored `output/` and are not release artifacts.

The narrow host-launched dynamic-runtime pytest was not counted as a Windows pass. Files created
directly by Windows appeared to a Linux container as mode 0777/UID 0, and the runtime correctly
rejected them under `MCP_REQUIRE_SECURE_SECRET_PERMISSIONS=true`. The canonical workflow passed
because the Linux deployment-worker container created UID/GID 10001 mode-0600 mounts. The required
Linux CI job must still pass `test_dynamic_runtime_docker.py` on the exact pull-request head.

## Gates that remain external or intentionally unperformed

The release is prepared for review, but publication remains blocked until each applicable item in
the release checklist has evidence:

- successful hosted CI, Security, dependency-review, CLA, and repository-rule checks on the exact
  pull-request head and later on the merged `master` SHA;
- Linux execution of the narrow dynamic-runtime Docker acceptance test;
- effective branch/ruleset, CODEOWNERS, administrator enforcement, private vulnerability
  reporting, Actions OIDC/GHCR permissions, and founder-approved CLA service configuration;
- hardened supported Linux x86-64 target host capacity, access, firewall, Docker-socket boundary,
  private secrets/key escrow, public DNS/TLS/ACME, secure cookies/headers, monitoring/alerts, and
  incident contacts;
- live OpenRouter model/quota/quality, real upstream DNS/TLS/credentials, any selected external
  OIDC provider, and named MCP-client interoperability;
- coordinated encrypted backup plus isolated restore, accepted RPO/RTO, credential decryptability,
  active-runtime recovery, and application rollback rehearsal;
- tag-triggered source/image SBOMs, checksums, Cosign bundle/signatures, GHCR digests,
  provenance/SBOM attestations, and GitHub Release assets.

The repository is private, and the first pull-request run confirmed that GitHub's dependency-review
action is unavailable until Dependency Graph and GitHub Advanced Security are enabled for the
repository. That is an external repository/billing setting: enable it and rerun the gate before
merge; do not bypass or convert the action failure into a warning.

Local fixtures, a green pull request, or a successful release workflow must not be represented as
proof of those operator/environment gates.

## Final publication commands after acceptance

After the pull request is accepted, merge without bypass, wait for successful CI and Security push
runs on the exact merge commit, finish the checklist, and then run from a clean checkout:

```bash
git switch master
git pull --ff-only origin master
python scripts/release_version.py --check
git status --short
git tag -s -a v1.0.0 -m "MCPlica v1.0.0"
git push origin v1.0.0
```

Use `git tag -a` only if the project's approved identity policy does not support signed tags. Do
not create a lightweight tag, move/reuse a tag, publish `latest`, push images manually, or deploy
production from this preparation branch.
