# MCPlica v1.0.0-rc.1

Status: public release candidate. This prerelease is intended for evaluation and integration
testing. It is not production certification, and no final `v1.0.0` release is implied.

## Release summary

MCPlica v1.0.0-rc.1 is the first public source and container candidate for the self-hosted
API-to-MCP control plane. It provides one canonical path from versioned OpenAPI or API Inventory
input and supporting documentation through deterministic manifest compilation, validation,
isolated MCP runtime deployment, authenticated tool and resource execution, rebuild and
redeployment, and immutable-build rollback.

The release workflow produces three images—`backend`, `frontend`, and `runtime`—plus source and
image SPDX JSON SBOMs, checksums, a keyless Cosign bundle, image signatures, and registry-attached
provenance and SBOM attestations. Publication is allowed only after required checks pass for the
exact independently reviewed `master` commit.

## Upgrade and migration

The database target is the single Alembic head `0025`. Existing pre-v1 installations must:

1. read [the upgrade guide](../operations/upgrade.md), take a coordinated backup, and rehearse on a
   restored non-production copy;
2. set `MCPLICA_VERSION=1.0.0-rc.1` in the private environment and remove the obsolete operator-set
   `MCP_RUNTIME_VERSION` value;
3. stop the API and workers, run the explicit migration job, then recreate application services
   from verified digest-pinned candidate images;
4. rebuild historical Builds whose frozen source, authentication, or index provenance is reported
   untrustworthy; and
5. validate login and CSRF, parsing, build validation, an existing runtime, a new deployment,
   authenticated MCP execution, and rollback before resuming changes.

Migration `0020` normalizes legacy constraint names. Migrations `0021` through `0025` add explicit
source and build identity plus execution fencing. `0021` deliberately rejects downgrade when a
restored source selection cannot be represented by the old schema. Never force that downgrade;
restore a compatible recovery point or retain the migration.

## Compatibility

Production support targets a hardened Linux x86-64 Docker host using Compose 2.24.4 or newer.
Windows Docker Desktop is a development and acceptance environment. macOS, arm64, Kubernetes,
Swarm, Podman, rootless Docker, and multi-host or high-availability operation are not certified for
this candidate. See [the compatibility matrix](../compatibility.md).

MCP clients must support Streamable HTTP and the configured bearer or OIDC `Authorization` header.
Specific editor and desktop clients and external identity providers require target-environment
acceptance.

## Known limitations and external prerequisites

- OpenRouter credentials, model access, quota, cost behavior, and model quality are external.
  Deterministic fixtures do not certify the live provider.
- Public DNS, ACME and TLS issuance, firewall policy, host hardening and capacity, production secret
  custody, registry permissions, external OIDC, alerting, incident contacts, CLA status, repository
  rules, and vulnerability intake must be verified in their real environments.
- Backups require coordinated PostgreSQL, artifact, runtime-root, key, and image evidence. The
  repository cannot certify an operator's encrypted backup, RPO/RTO, or isolated restore drill.
- The supported topology is single-host Docker Compose with local filesystem artifacts. There is
  no built-in backup scheduler, multi-host failover, SaaS tenancy or billing, chat or agent runtime,
  or human approval gate for runtime calls.

Unchecked production gates remain blockers; a prerelease does not waive them. Use the
[release checklist](../maintainers/release-checklist.md) for sign-off.

## Verification and publication

After the candidate pull request has an independent approval and every required check passes on
its exact head, merge it and wait for successful CI and security indexing on the merge commit.
Then create one annotated tag:

```bash
git switch master
git pull --ff-only origin master
python scripts/release_version.py --check
python scripts/checksum_manifest.py --check
git tag -s -a v1.0.0-rc.1 -m "MCPlica v1.0.0-rc.1"
git push origin v1.0.0-rc.1
```

If an approved signed-tag identity is unavailable, use an annotated tag without `-s`; never use a
lightweight tag or move and reuse a published tag. Verify the resulting assets and image digests
with the [release process](../maintainers/releasing.md) before any production use.
