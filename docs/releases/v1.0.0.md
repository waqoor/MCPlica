# MCPlica v1.0.0

Status: release candidate documentation. The `v1.0.0` tag, GitHub Release, and production images
must not be created until the release-readiness pull request is merged and every required hosted
and target-environment gate is complete.

## Release summary

MCPlica v1.0.0 is the first stable source and container release of the self-hosted API-to-MCP
control plane. It provides one canonical path from versioned OpenAPI/API Inventory and supporting
documentation through deterministic manifest compilation, validation, isolated MCP runtime
deployment, authenticated tool/resource execution, rebuild/redeployment, and immutable-build
rollback.

The release contains three container images—`backend`, `frontend`, and `runtime`—plus source/image
SPDX JSON SBOMs, per-component evidence/checksums, an overall `SHA256SUMS`, a keyless Cosign bundle,
image signatures, and registry-attached provenance/SBOM attestations. The publication workflow
creates these only after successful CI and Security push runs for the exact tagged `master` commit.

## Upgrade and migration

The database target is the single Alembic head `0025`. Existing pre-v1 installations must:

1. read [the upgrade guide](../operations/upgrade.md), take a coordinated backup, and rehearse on a
   restored non-production copy;
2. add `MCPLICA_VERSION=1.0.0` to the private environment and remove the obsolete operator-set
   `MCP_RUNTIME_VERSION` value—Compose now derives runtime version from the release authority;
3. stop API and both workers, run the explicit migration job, then recreate application services
   from verified digest-pinned v1.0.0 images;
4. rebuild historical Builds whose frozen source/auth/index provenance is reported untrustworthy;
5. validate login/CSRF, source parsing, 100% build validation, an existing runtime, a new deployment,
   authenticated MCP execution, and rollback before resuming changes.

Migration `0020` normalizes legacy constraint names. Migrations `0021` through `0025` add explicit
source/build identity and execution fencing. `0021` deliberately rejects downgrade when restored
source selection cannot be represented by the old schema. Never force that downgrade; restore a
compatible pre-upgrade recovery point or retain the migration.

## Compatibility

Production support targets a hardened Linux x86-64 Docker host using Compose 2.24.4 or newer.
Windows Docker Desktop is a development/acceptance environment. macOS, arm64, Kubernetes, Swarm,
Podman, rootless Docker, and multi-host/high-availability operation are not certified for v1.0.0.
See [the full matrix](../compatibility.md).

MCP clients must support Streamable HTTP and the configured bearer/OIDC `Authorization` header.
Specific editor/desktop clients and external identity providers require target-environment
acceptance; no client is certified merely from configuration syntax.

## Known limitations and external prerequisites

- OpenRouter keys, available model IDs, quota/cost behavior, and model quality are external. Local
  deterministic fixtures do not certify the live provider.
- Public DNS, ACME/TLS issuance, firewall policy, host hardening/capacity, production secrets and
  escrow, registry permissions, external OIDC, alerting, incident contacts, CLA status, branch
  rules, and private vulnerability reporting must be verified in their real environments.
- Backups require coordinated PostgreSQL, artifact, runtime-root, key, and image evidence. The
  repository documents the process but cannot certify an operator's encrypted backup, RPO/RTO, or
  isolated restore drill.
- The supported topology is single-host Docker Compose with local filesystem artifacts. There is
  no built-in backup scheduler, multi-host failover, SaaS tenancy/billing, chat/agent runtime, or
  HITL approval gate.

Unchecked production gates remain blockers; they are not waived by local tests. Use
[the release checklist](../release/release-checklist.md) for sign-off.

## Verification and publication

The release-preparation evidence record contains exact local results and identifies what only the
pull-request/hosted workflows can prove. After merge, wait for successful CI and Security runs on
the merge commit, complete the checklist, then create one annotated tag:

```bash
git switch master
git pull --ff-only origin master
python scripts/release_version.py --check
git tag -s -a v1.0.0 -m "MCPlica v1.0.0"
git push origin v1.0.0
```

If signed tags are not configured under the project's identity policy, use an annotated tag only;
do not create a lightweight tag. Never move/reuse the tag. The tag push is the sole publication
trigger. Verify the resulting assets and image digests using the release process before configuring
production Compose.
